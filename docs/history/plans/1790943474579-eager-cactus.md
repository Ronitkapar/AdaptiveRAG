# Phase 8 — Corpus re-extraction and re-baseline

## Goal

Two questions, both currently unanswerable:

1. **Does the corpus defect explain the reranker failure?** We diagnosed the mechanism (column-interleaved text, 1.4% glued tokens, far off MS-MARCO's distribution). Testing it requires clean text.
2. **Was "dense dominates hybrid" an artifact of the same defect?** Hybrid and rerank both degrade on garbled text in different ways. Nobody knows how much of the E1 ordering is corpus-induced.

**No retrieval method is removed.** All five arms are re-run and reported side by side.

## Framing: this is a before/after study

The new corpus **coexists** with the old one — new `corpus_version`, new BM25 index directory, new Qdrant collection. Nothing is overwritten. Phase 7's results stay valid and become the *before* arm. Phase 7 remains a completed experiment; Phase 8 is an addition, not a rewrite. `strategy_cost_ms.json` keeps one frozen value per corpus version rather than being silently redefined.

## Step 0 — Pre-register the all-pairs comparisons

Write into `docs/phases/phase-8.md` the exact comparison list and correction rule **before the numbers exist**:

- 5 systems → **10 unordered pairs** via `itertools.combinations`
- Holm adjustment **within each metric across all 10 pairs**, `family_size` recorded per metric
- Metrics: `recall_at_5`, `mrr`, `ndcg_at_5`, `total_latency_ms`
- Disclosure that E1 point estimates were observed before these tests were specified, so they are **post-hoc/exploratory within this program** — pre-registered, but not originally planned

New driver `compare_all_pairs(rows, systems, metrics, ...)` in `statistics.py`, alongside the existing `paired_comparisons` / `compare_systems` / `compare_variants`. Reuses `compare_metric` unchanged; only pair enumeration and the correction family change. Offline — reads existing `rows.jsonl`, no network.

## Step 1 — Two-column extraction fix

`normalizer.py:92-116` merges chars within 3.0 pt of `top` into one line. In a two-column page both columns share `top`, so they merge and then get joined left-to-right by `x0` — exactly the glued-token symptom. `RawChar` already carries `x0`/`x1`/`top`/`bottom`, so the extractor is untouched.

- **New `_detect_columns(chars, page_width)`** — project char coverage onto the x-axis; find an interior gap that is wide (>= 6 pt), near page centre (within 25% of width), and persists across most of the page's vertical extent. Return column ranges, or `None` for single-column pages.
- **`_cluster_chars_into_lines(chars, column_ranges)`** — assign chars to columns by `x0`, cluster lines *within* each column using the existing 3.0 pt rule, emit reading order as left column top->bottom then right column top->bottom. Chars forming runs that **cross** the gutter are full-width elements (titles, wide figures, tables) and are not split.

### Validation gates — measured, not asserted

| Gate | Criterion |
|---|---|
| Glued-token rate | 1.4% baseline -> near zero on two-column pages |
| Spot check | a known sentence from a known two-column paper (`dpr_karpukhin_2020.pdf`) reads cleanly end to end |
| Single-column regression | output byte-identical to current behaviour on single-column pages |
| Reading order | first N elements of 2-3 papers hand-verified against the PDF |
| Chunk delta | report how many chunk texts change |

No re-ingestion until the single-column regression gate passes. A naive split that scrambles reading order would make everything worse; that is the main engineering risk.

## Step 2 — Re-ingest as a new corpus

## Step 4 — Re-validate gold labels

Determines whether the schedule holds.

- `relevant_documents` — **document-level, survives.** `_recall_at_k` and `_reciprocal_rank` key on `metadata.document_id`, so Recall@5 / MRR / Hit@5 stay valid without touching the 107 records.
- `relevant_chunk_ids` — **chunk-level, must be re-verified.** Feeds `nDCG@5` and E8's pre-escalation chunk ids.
- Attempt a mechanical remap by `(document_id, chunk_index)` where ordering is stable, then re-run `scripts/validate_phase7_dataset.py` end to end (S1-S5, G1-G7).
- **Bonus signal:** cleaner text may let some of the 159 `indeterminate` G7 quotes verify — an independent improvement in evidence quality.
- **Audit, not just remap:** the relevance judgments were originally made by reading garbled text. Some may not hold on clean text. Records with low remap confidence get re-read individually.

## Risks, stated plainly

1. **A null result is a real possibility.** Clean text may not rescue the cross-encoder. Pre-registering makes that a legitimate finding rather than a disappointment — recorded before the effort, not after.
2. **Reading-order regression** is the main engineering hazard (Step 1).
3. **Chunk-id remap may fail** if boundaries shift too far, forcing manual re-annotation. Biggest schedule risk; lives in Step 4.
4. **`corpus_version` change breaks Phase 2-6 comparability** — mitigated by coexistence, not eliminated. Those results remain true *of the old corpus*.
5. **Some judgments were made on bad text** and may need revision regardless of remap success.

## Explicit non-goals

No retrieval method is removed. No router, ladder, or threshold change — that stays out until this evidence exists. No generation evaluation. No composite score. Nothing under `experiments/phase7/` or the old corpus is modified.
